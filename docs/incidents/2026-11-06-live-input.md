# 长会话实时输入、压缩与重连修复

## 复现与根因

- 运行数小时的原生轮次在发送前被请求 `thread/turns/list(itemsView=full)`。该读取包含完整工具输出，超过 WebSocket 的 2 MiB 限制。对实际会话做只读复现，3.448 秒后得到 `WS_ERR_UNSUPPORTED_MESSAGE_LENGTH / Max payload size exceeded`，与两次输入失败的 3.457 / 3.354 秒耗时一致。此时尚未调用输入接口，却被泛化为“结果未知，需要用户核对”。
- 压缩入口只允许 `idle`，把原生可以执行 `/compact` 的 `systemError` 状态挡在平台外。请求拒绝又显示成“压缩失败”；晚到 HTTP 错误还能覆盖已经观察到的原生运行状态。
- 重载把 CLI/引擎版本号完全相等当作前提。本机 CLI 0.167.0、共享引擎 0.166.0，即使协议握手成功也被要求先升级共享服务。

## 修改

1. 已有实时订阅直接提供活动轮次 ID 和有界的用户回执。运行中追问使用 `turn/steer`；冷读取只获取摘要，排除完整工具输出。活动轮次已结束/变化的明确拒绝可以安全改用 `turn/start`；普通传输未知不会切换路径重发。原生输入不再等待终端附着。
2. 压缩期间确实不可追加时才暂存到原生队列。平台持久化的只是自身排队项身份，空闲事件后调用原子的 `thread/queue/start`；不重新粘贴正文，不抢占其他来源的队列头，不增加轮询。原生取消/消费后清理身份。
3. 根据是否已经派发区分“未发送”和“结果待确认”。收到晚到原生回执时清除提示；草稿和后续编辑保留。
4. 允许错误状态的原生压缩；区分“压缩未启动”“状态待确认”和真正执行失败。原生开始/结束事件优先于晚到的 HTTP 错误。
5. 重连预检使用握手与配置读取。版本差异显示实际情况，不再强制重启共享引擎；协议确实不可访问时仍在停止客户端之前拒绝。

## 验证范围与限制

使用模拟原生服务验证超大记录、实时追加、派发前后断开、重复提交身份、压缩后队列的原子接续及持久化恢复。桌面浏览器覆盖运行中追问、原生队列、Fast、同一会话重载、草稿和图片保留。没有向真实 Agent 发送测试消息，没有重启共享原生引擎。

最终验证：服务端全量 770 项通过、1 项既有跳过；前端 440 项通过（`--maxWorkers=2`）；桌面 controls/reload 两项通过；两侧构建和更新安全检查通过。首次高并发前端运行有两项既有 Markdown 图片预览用例超时，定向和降低并发后的全量均通过，未修改相关产品代码或放宽断言。

实时追加表示原生已接收；正在执行的工具何时处理新信息由原生 Agent 的执行边界决定。上游内容风险拒绝仍按原生错误展示，不通过平台重试或改写绕开。重连不等于引擎升级，实际引擎版本继续如实显示。
