# Agent 协作

使用平台提供的标签页身份。只要你向其他标签页派工，就对这部分交付负责。在明确的项目范围和授权内拆解工作、确认先后依赖、制定验收条件，并持续处理阻塞和核对结果。

**只有最上层负责协调的 Agent 与用户沟通。** 有 `parent_tab_id` 的子 Agent，通过 `agent-docs` 与父 Agent 和其他标签协作。需要澄清、遇到失败或缺少授权时，先[向父 Agent 回传](references/collaboration.md#问题与报错如何上报)，避免直接向用户发出问题或原生交互请求。父 Agent 先解决能自行处理的问题，再统一向用户请示必须由用户决定的事项，并通过协作消息把结论发回子 Agent。

**Codex 子标签页派工最高用 `gpt-6.2-sol`，推理强度最高 `high`，统一关闭 Fast。** `gpt-6-luna` 的推理强度可用到 `max`。按任务难度选够用的配置。新建和复用子标签页都先按[配置分配](references/allocation.md#派工上限)核对模型、强度和速度，再投递任务。

1. 在本技能目录执行 `python3 scripts/platform_api.py capabilities`。按响应中的 `source_tab_id`、`project_id`、`operations` 和 `limits` 确认自己能做什么。客户端自动使用运行时凭据。
2. 派工前用 `list-tabs --children --include-ended` 核查直属子标签，读完分页并处理 `cleanup_review`。优先沿用职责和上下文匹配的标签，调整模型参数时原地更新。对已验收且无后续工作的标签，在有权限时关闭并保留历史。需要继续使用或保留待命的标签明确记录去向。只有找不到合适的已有标签时才新建。详见[派工前核查](references/tabs.md#派工前核查)。
3. 按[协作规范](references/collaboration.md#派工与验收)派工。用负责人自己的口吻，直接写清目标、范围、依据、验收条件和交付物。需要汇总的并行任务先开批次，派发时带上 `batch_id`，派发结束后封批。忙碌子标签的追加任务可以选择在当前轮结束后交付。平台在收齐或到期时通知父标签页一次。普通进展直接入箱，需马上协调的阻塞可立即通知。执行方引用原消息 ID 回传。Agent 间消息命中发送保护规则时，平台在条件允许的目标标签内自动简要压缩，再继续原消息的投递。
4. 父标签页协调依赖和资源，处理阻塞与验收缺口，跟进到形成可验证的交付结论。等待时推进当前目标中未委派且可独立完成的工作。没有可推进的事项时结束当前轮次，留好待回传清单。
5. 回传只表示本轮子任务给出了结论。父标签页核对证据及待追问事项，判断是继续用原来的子标签页跟进、保留待命，还是在有权限且已收尾时关闭。关闭保留历史。只有用户明确要求永久删除历史时才指定历史删除。

| 当前要做什么 | 按需读取 |
|---|---|
| 确认身份、权限、接口和错误处理 | [平台身份与 API](references/access.md) |
| 查找、查看进展、新建、关闭或永久删除会话 | [标签页操作](references/tabs.md) |
| 发任务、查收件箱、关联原消息回传 | [消息投递](references/messages.md) |
| 发起并行任务，收齐或到期后集中唤醒 | [协作批次](references/batches.md) |
| 查看模型、推理强度与 Fast，原地修改已有子标签 | [配置分配](references/allocation.md) |
| 约定消息内容，处理多来源任务，组织并行协作 | [协作规范](references/collaboration.md) |

为每个写操作保留独立的 `request_id`。超时或结果不明时查询原请求。任务结果按收到的 `message_id` 回传，平台会核对这条消息确实发给了当前标签页，并找到原始发送方。遇到缺失能力、凭据失效或权限拒绝时，报告具体受阻的操作。
